# 机器人感知链路性能测量：2026-10-20

设备：192.168.98.244。使用已安装包与当前部署配置，E01_best.engine，双目 batch=2，输入 640×640；相机 VGA 672×376、30 FPS；目标输出 50 Hz；Viser 显示图像、关闭点云。nvpmodel 查询显示 25W。

通过临时脚本对实际节点方法添加 perf_counter 计时，使用独立 ROS_DOMAIN_ID=97，避免测试发布进入控制域。每组运行约 25 秒，阶段统计和发布频率剔除前 20 帧。未修改部署配置、engine 或运行代码。测试结束已关闭相机与临时 Viser 服务。

开启 Viser：预热后发布调用频率 **17.09 Hz**，约 **58.51 ms/轮**；关闭 Viser：**19.09 Hz**，约 **52.40 ms/轮**。这是节点发布端计时，并非外部 ros2 topic hz 接收端测量；本次未连接浏览器，未覆盖浏览器连接时的额外负载。与用户观测的 15 Hz 有差异，不能直接断言接收端或其他负载没有影响。

检测总计与子项为嵌套计时，不能重复相加。检测总计约 46.83 ms，占整轮约 80%；Viser 约 6.28 ms，占约 11%。相机 grab 约 1.30 ms，单目 retrieve_image 平均约 1.07 ms。定位、匹配、跟踪合计约 0.32 ms。调度等待约 0.009 ms，没有明显限频等待。

YOLO 子阶段是 CPU 墙钟调用耗时，CUDA 异步执行与框架同步可能影响阶段归属；不是 CUDA event 测得的纯 kernel 耗时。检测总耗时更适合判断整体瓶颈。测试主要覆盖当前静态场景，候选框较多时后处理成本可能不同。

## 优化顺序

1. 优先优化模型与 engine：当前输入、输出绑定均为 FP32，内部层精度未能确认（engine inspector 仅提供层名）。应先核对导出精度，再用独立文件对照 FP16 engine；不能仅凭配置 half=true 认定已有 engine 是 FP16。不要覆盖现有可用 engine。
2. 评估更小的 engine 输入尺寸（如 512 或 416），或更轻模型。当前固定输入为 2×3×640×640，应配套导出新 engine，并验证远处小球召回率与双目定位误差，收益需实测。
3. 预处理约 9.57 ms，值得继续拆解 resize/letterbox、布局转换、拷贝和归一化，评估复用缓冲区或 GPU 预处理。后处理约 4.92 ms；日志显示 torchvision NMS 使用纯 torch fallback，可对照兼容的原生算子，但它不是当前最大耗时项。
4. Viser 降频或移至独立工作线程，避免每帧同步编码和更新；关闭 Viser 的实测收益约 2 Hz。异步方案需复制必要数据、限制队列长度并丢弃过期显示帧。
5. 当前 ROS 发布约 0.74 ms，定位跟踪约 0.32 ms，优先优化这些环节收益很小。
6. 30 Hz 需要整轮低于 33.3 ms，当前开启 Viser 需减少约 25.2 ms。50 Hz 需要整轮低于 20 ms，并调整当前实际 30 FPS 的相机采集设置；只调 deploy_packet_rate_hz 无法实现。

原始统计：profile_baseline.json 与 profile_no_viser.json。此次仅完成性能测量，未验证优化后的精度或速度。
