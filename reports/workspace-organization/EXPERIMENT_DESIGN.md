## 拟议结构：先审模板，再创建真实目录

```text
experiments/
├── E00_original/
├── E01_finetune/
├── E02_c3k2/
├── E03_p2/
└── E04_neck/
    ├── PLAN.md                         # 假设、控制组、保持不变的因素
    ├── recipe.yaml                     # 人工可读设计；具体训练配置仍走既有入口
    └── runs/<UTC>_s<seed>_<suffix>/
        ├── run.yaml                    # 单次运行的事实、状态与引用
        ├── config/                     # 有效参数、结构和数据指纹快照
        ├── environment/                # 版本/设备信息及依赖清单
        ├── train/                      # 本次训练的原始输出；E00不创建虚构训练结果
        ├── evaluation/
        │   ├── val/<eval_id>/
        │   └── test/<eval_id>/
        ├── deployment/<device>/<benchmark_id>/
        └── ARTIFACTS.json              # 权重、指标、导出模型的路径与SHA256
benchmarks/
├── runs.csv                            # 每行引用一个真实run
└── comparison.md                       # 明确相同数据/设备/口径后的比较
```

## 每个 run 的最小可复现记录

| 范畴 | 必填内容 |
| --- | --- |
| 身份和状态 | experiment_id、唯一 run_id、UTC 开始/结束时间、planned/running/complete/failed/interrupted、父 run、失败原因 |
| 源码 | commit（可得时）、是否含未提交改动、实际差异/脚本 SHA256；不能只记分支名 |
| 结构与初始化 | 架构文件/哈希、类别数、输出 stride、参数量；初始化模式、权重路径/哈希、来源 run；兼容/总张量数、missing/unexpected keys、新模块初始化及曝光史 |
| 数据 | dataset_version、共享配置/解析后 YAML/metadata SHA256、冻结 manifest SHA256、train/val/test 名单和图像+label 内容 manifest SHA256、实际张数、划分关系及排除规则 |
| 训练 | 最终生效参数快照、随机种子、deterministic、设备、依赖版本、epoch/batch/imgsz/优化器/增强、best 选择规则与 best/last 权重哈希 |
| 评估 | 输入权重哈希、类别映射、实际样本清单/哈希、split、imgsz/letterbox/min_conf/conf/match_iou/NMS/max_det/模型头模式、指标/逐图记录路径 |
| 部署 | 导出模型哈希/格式/精度、目标设备/电源模式/驱动和运行时、输入形状/batch、校准集哈希、计时范围、warmup/重复数、同步方法、延迟/吞吐/内存 |
| 结论 | 对照 run、收益/成本、失败或未测内容；未执行的指标填 null/not_measured，不填0冒充已测 |

recipe 表示意图，run 记录实际生效值。启动前固化所选数据版本和指纹，后续共享配置切换不能改写旧 run 的数据来源。大规模图像不必在每个 run 再复制一份；引用冻结 manifest 与内容哈希即可。运行 YAML 含本机绝对路径时，另保留逻辑版本与仓库相对引用供迁移重建。

## 独立运行与不可覆盖

1. 每次新训练、重启失败实验、独立评估和部署测量均取得新 ID；例如 `20261019T120000Z_s42_a1b2c3d4`。时间示例仅说明格式，不代表该时刻已执行。
2. 真实 run 使用独占创建，发现目录已存在就失败；保留 `exist_ok: false`，不要把原目录当“最新结果”覆写。框架自动递增的实际输出目录也要写入 run，而非从预期名字猜测。
3. 恢复训练属于同一逻辑 run 的明确恢复事件，记录 checkpoint 哈希、恢复时间和原参数；因改变数据/结构/超参数而重新训练则创建新 run。
4. run 运行中可追加状态和日志；完成后冻结其配置、原始输出、模型及评估记录。订正说明通过新增记录引用旧 run，不偷偷替换原结果。
5. `benchmarks/runs.csv` 只汇总有来源且完成的记录，不能仅凭最新目录或最好看的数字挑选结果。支持多种子时预先选定同一组 seeds，报告各次结果及均值/波动，不能只报最好一次。

## Val、Test 与模型选择

- 训练、early stopping、超参数、结构、阈值和候选模型选择使用 Train/Val。部署 INT8 校准使用规定的训练子集，记录名单，不用 Test 校准。
- 在接触 Test 前冻结候选模型、选择准则、工作阈值、模型/代码/数据哈希及评估口径。对最终候选采用预先声明的同批比较，不把反复查看 Test 后的调参结果仍称一次最终测试。
- Test 的每次访问都保留单独 eval_id、时间、模型哈希与原因；不通过更名、换目录或换 run 擦除访问史。失败的测试也应记录，而非仅保存成功结果。
- E00 与 E01–E04 显式记录不同的类别映射；比较足球类别指标时使用相同数据、图像处理和候选/匹配口径。
- 核心质量表至少记录 mAP50、mAP50–95、固定阈值 P/R/F1、无球图片误报率（含负样本数）、小目标/遮挡/模糊分组及样本量。场景可重叠，不把分组数量相加当总体数量。
- v1 Test 的有效结论是当前同场次片段留出上的表现；独立场次泛化另需新数据和新版本，不能用命名替代来源独立性。

## 部署性能的可比边界

模型质量与部署速度分别记录。当前评估脚本的后端平均计时、含加载/首次 warmup 的墙钟吞吐不能直接当部署 benchmark。未来在同一目标设备、输入尺寸、batch、运行时、精度与电源模式下比较：

- 设备型号、CPU/GPU/加速器、OS/驱动、CUDA/cuDNN/TensorRT/ONNX Runtime 等实际使用版本；设备未指定时填待定，不预填一个并未测过的设备。
- PT/ONNX/engine 等模型格式、导出 SHA256、FP32/FP16/INT8、固定/动态 shape、batch 与校准来源；质量指标须对应实际部署文件。
- 明确计时是否包含解码、resize/letterbox、拷贝、推理、NMS和输出；设备异步执行需明确同步。区分模型延迟、吞吐与相机到结果的端到端延迟。
- 记录 warmup 数、测量重复数、输入序列、mean/p50/p95 延迟、吞吐 FPS、端到端 FPS、峰值内存；需要能耗结论时再记录实测功耗/温度/热稳定情况。未测项保留 null。
