## 建议分层

| 内容 | 建议保存方式 | 发布前应具备的事实 |
| --- | --- | --- |
| 源码、通用配置、测试、实验设计、结构定义 | 普通 Git 文本 | 无密钥/本机私有信息；依赖与运行要求明确 |
| 数据版本 manifest、split 清单、内容哈希、采集/标注规范 | 普通 Git；大文件另评估 | 字段不泄露不应公开的信息；能指向可获取的合法数据 |
| 精简实验索引、指标摘要、关键图表、方法结论 | 普通 Git 中保留小型可审阅材料 | 指向真实 run、模型/数据哈希，清楚标注未测项及数据局限 |
| 原始视频、完整图片集及多个数据版本副本 | 本地保留；授权明确后再选数据发布载体 | 来源、许可/授权、再分发范围、隐私和存储容量已有结论 |
| 原始参考权重、训练 best/last、导出 ONNX/engine | 本地不可覆盖；授权明确后可评估 Release、模型托管或 LFS | 来源/许可证、哈希、架构、类别映射和运行要求可追溯 |
| 中间 checkpoint、逐轮大图、调试预测、可再生缓存/build | 本地 run/缓存；仅保留必要审计引用 | 对失败或关键结论有价值的记录先纳入保留清单，不按名字盲删 |
| CSV/label 恢复副本、完整恢复归档 | 正式数据外独立保存 | 能校验和恢复；不将唯一备份误当临时文件 |

数据与权重保留在本地不等于具有公开再分发许可。用户希望开源工作路线时，可先发布授权明确的代码、实验设计、方法、哈希和结果摘要；许可未明的资产不上传，也不通过下载脚本、镜像或公开附件绕过许可确认。

## 选择 Git、LFS 或外部载体

- 普通 Git 适合可审阅、体积可控、需要逐行追踪的源码和实验元数据。未完成资产清单与范围确认前，不进行全量暂存。
- LFS 可用于确需随仓库版本化的二进制，但不能自动解决许可、配额、下载负担或历史已有体积。只有明确容量、访问方式和协作需求后才选择；添加新 LFS 规则与迁移既有历史是两件事。
- Release / 数据或模型托管适合单独版本发布的大资产。仓库保留版本号、下载地址、字节数、SHA256 和许可说明；先确认权限与来源，不能把“计划发布”写成“已经可下载”。
- 外部存储与普通 Git 中的 manifest 应共同支持复现：无论资产在哪里，记录结构、初始化、数据内容、环境和结果哈希，不仅给一个会变化的路径或文件名。

本轮只提出选择标准，不指定服务、不建远端、不下载或上传，也不执行历史迁移。

## 后续获准上传时的轻量清单

1. 按任务范围检查真实变更和暂存清单，保留用户已有改动；再次确认新 run 路径的大输出是否意外进入提交。
2. 区分代码/元数据、可公开样例、完整数据、原始/训练权重，逐类记录来源与授权。资产授权未明时先完成文本成果，不擅自补一个无法代表第三方材料的统一许可证。
3. 为要发布的资产建立版本、字节数、SHA256、架构/类别和来源指针；下载/加载时验证哈希。原始参考权重保留原字节，不为视觉整洁改写 checkpoint。
4. 根据当前仓库体积与目标资产规模决定普通 Git、LFS 或独立载体；先展示具体方案，再执行影响既有历史或远端的步骤。
5. 依既有项目约定完成任务相关验证、中文 commit 及普通推送后，核对本地/远端提交编号。单独出现 `Everything up-to-date` 不足以证明大包推送成功。

## 本轮明确不执行

没有执行 Git add/commit/push、GC、prune、repack、历史重写、LFS 迁移、删除临时对象、回滚或修复远端。`tmp_obj_*` 和松散对象的来源、可达性及清理收益尚未做获准的完整调查，不提供带删除副作用的“清理命令”。

长期组织的收益应先来自清楚的入口、数据与初始化来源、每次运行记录和按需发布。对象存储清理属于独立维护工作，不能与本轮只读审计混在一起。
